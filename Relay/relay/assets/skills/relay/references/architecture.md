# 架构与机制

## 对象

域是账号和消息的命名与认证边界。账号有内部 ID、唯一 username、可重复的显示 name、机器 token、启用状态和可选的账号创建权限。username 统一为小写，创建后不可修改或复用；不要把显示名当身份。

账号 manager 关系用于管理自己创建的账号及其后代。群有独立的群主和成员关系；能管理一个账号不等于能管理它参加的群。聊天服务不根据 manager 关系决定谁是外部应用的用户或主管。

## 服务与存储

```text
浏览器 / HTTP 客户端 / MCP 客户端
              ↓ 认证和权限检查
        Relay 服务与业务存储
              ↓
        SQLite 持久数据
              ↓
     长轮询通知 / 待收队列 / 会话历史
```

`server.py` 提供网页、HTTP、长轮询和进程生命周期；`mcp.py` 提供同一业务语义的机器工具；`store.py` 保存域、账号、私聊、群、成员与消息；`browser_auth.py` 管理浏览器密码、通行密钥和会话。HTTP/MCP 共用服务数据与权限，而非两套独立消息。

同一数据目录由单个服务持有。默认数据根 `~/.relay/`，`RELAY_HOME` 或 `--root` 可覆盖。服务默认监听 loopback；公网入口、TLS 和进程托管由部署者配置。

## 消息生命周期

发送成功表示事务落库，不等对方在线或回复。私聊有发送者与收件者；群消息保存群历史，并为其他当前成员生成独立的入站投递。每个收件人的确认状态独立。

`receive` 返回自己的未确认投递，重复读取仍可看到它；`ack` 使它退出待收队列；`read=true` 同时标记聊天已读。历史保留，但群历史还受当前成员关系和本次入群边界约束。网页打开会话会把已加载的入站消息标记已读，可能与同账号的其他消费者共享确认状态。

`GET /api/wait` 只返回 latest/pending 等提示，不含业务正文、不确认。通知是可重复的提示，客户端再读取原消息。client_id 为同一发件人的发送操作提供幂等重试；复用到不同内容会冲突。没有“接收、执行外部任务、回复”跨系统恰好一次事务。

## 认证

MCP 使用机器 Bearer token。HTTP API 可使用账号 Bearer，浏览器也支持自己的 HttpOnly session Cookie。密码/通行密钥用于网页登录，机器 token 仍是另一种凭据；更改密码不等于重置 token。账号停用及 token 撤销即时影响对应认证，管理祖先停用会影响其后代账号的可用性。

每个域分别登录。浏览器域切换不会把消息投递到另一个域。HTTPS、Cookie scope 和 WebAuthn origin 由部署配置决定，不能把不同端口本身理解成 Cookie 隔离。真机 Face ID 由用户设备完成，虚拟通行密钥测试只验证协议链路。
