# Aster 边界与后续建议

本轮未修改 Aster 仓库。Squad 运行时只使用公开 SDK、公开 Thread 配置文件和公开事件 SDK，没有访问私有 Session 或 pin 方法。

第一版不需要新的运行时能力：MCP、skills、程序发生器、记忆与正常恢复已经足够。没有加入自定义 base instruction；agent 创建时的身份放在独立 instruction，经历与培训结论留给它维护长期记忆。

后续值得向 Aster 提出的改进：

1. **更中性的 base instruction**。当前开头仍是 assistant，部分工作原则针对编程。可把通用职责、显式渠道、事件、记忆和权限边界保留在 base，把具体编程工作方式移入 skill。需要单独讨论原生终端的用户绑定，不靠聊天正文自称确认身份。
2. **公开的配置更新接口**。当前 SDK 文档只保证暂停、编辑配置、resume。Squad 遵循这一流程。未来可提供在 Step 边界原子更新 instruction/model/policy 的公开操作与结果事件，减少停启。
3. **更明确的外部事件持久确认**。当前 accepted 是入队，不等于持久提交；可靠消息消费需要稳定输入 ID、去重和明确的持久边界。第一版没有伪称已经解决任意崩溃下的恰好一次处理。
4. **文件读取的 allowlist**。现有沙箱是 workspace 可写、未匹配路径禁止访问，叠加 read/write/deny；可通过显式 `/=read` 开放其余文件。Squad 强制屏蔽自己的私有数据并预分配工作区，但没有把这个机制描述成完整容器或网络权限。
5. **可复用的事件源包**。目前 skill + Python 脚本 + register_program_generator 足够。等多个独立工具都需要监听，再考虑标准化事件源安装、凭据注入和状态查询，不急于设计新的 MCP 替代协议。

真实模型行为尚待用户选择模型并实际验收；当前所有自动化验证都不调用付费服务。
