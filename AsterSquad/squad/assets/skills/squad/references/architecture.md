# 架构与机制

## 对象和身份

| 对象 | 职责 |
|---|---|
| 工作台/Fleet | 注册多个空间与独立聊天域，代理用户网页，管理子服务生命周期 |
| Squad/空间 | 管理一组 agent、成员分支、模型 allowlist、授权和管理消息 |
| agent | 稳定 agent ID、域内唯一 handle、parent、instruction、模型和 grants |
| Harness Thread | 成员持久经历，Thread ID 与 agent ID 不同；正常修改和恢复沿用原 ID |
| worker | 一个进程托管一个成员的 Thread，用公开 SDK 与 Harness 交互 |
| Relay 域和账号 | 独立聊天身份，账号由宿主先创建/分配，再把凭据配置给成员 |

handle、agent ID、Thread ID 和聊天账号不是可互换的标识。查返回值建立关联，不由 slot 目录名猜身份。

## 进程与消息流

```text
用户浏览器 → Fleet 工作台 → Squad 控制器 → worker → Harness Thread
                       ↘ 独立 Relay 服务 ← 成员通过 Relay MCP 调用
                                                ↑
                              成员注册的长轮询监听 → 程序事件
```

控制器持有成员数据库、配置、凭据和审计，worker 通过 JSON lines 接收管理命令并返回状态。Harness 自己负责模型循环，Squad 不再实现另一套模型调度。Relay 的 HTTP、MCP 和网页使用自己的数据与权限规则，服务本身不导入 Squad。

创建成员依次校验名称/模型/授权、创建聊天账号、保存稳定身份及凭据、准备独立 workspace 和外部连接目录、挂载 MCP/skills、创建并启动 Thread。已有成员启动则恢复原 Thread。`online` 表示运行时启动成功；不能据此证明模型额度、监听或业务任务都健康。

## 分支与通信

parent/child 表示管理和权限转授关系。成员可以管理直接 child，向 parent/直接 child 发管理消息；平级日常协作经聊天模块。聊天中的账号管理或群主身份不自动产生 Squad 管理权。

管理消息先落库，离线时积压，在线后投递给 worker。accepted 仅表示 SDK 输入接口接受，不表示模型已读、持久事务提交或任务完成；崩溃点可能重复或丢失入队，应结合持久工作记录和回信核对。

## 生命周期与接入

配置运行中成员：正常暂停并保存 → 更新当前配置/instruction → 恢复同一 Thread。恢复、归档和重新开户是不同动作。归档保留原成员和 workspace，不复用 slot；恢复归档后仍需按需启动。

默认给每个 Squad 一个 Relay 域及成员账号，注入连接信息；成员依 Relay 指南自行建立监听。Harness 终端保留用户的直接输入通道。可信用户在创建时绑定，不由同事发来的聊天文本改写。

当前模块接入以宿主注册 MCP、skills、连接与权限为主，没有通用模块商店或任意插件安装接口。跨空间自动共享账号、统一网络管理权限等也不能由上述接入关系推导出来。

启动分两层：工作台设置控制宿主启动器是否随系统启动；空间设置 `restore_members` 控制该空间启动后是否恢复此前请求运行的成员，默认关闭。保存空间设置不会立即启动或暂停成员。显式启动记录运行意图，主动暂停或归档清除它；宿主安全停机保留它。空间启动且 MCP/Relay 就绪后，最多同时恢复两位，每次生命周期只尝试一次；已报错、主动暂停和归档成员跳过。未正常关闭的 Thread 不绕过恢复校验，Windows 管理员仍遵循 UAC。已暂停的空间不会因恢复设置自动开启。旧版成员级 `auto_start` 仅在尚未明确保存空间恢复策略时兼容；空间设置一旦保存即统一覆盖旧标记。
